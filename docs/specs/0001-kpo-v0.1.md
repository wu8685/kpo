# KPO v0.1 Behavior Specification

- Status: **Approved for implementation on 2026-08-12**
- Project: Knowledge Policy Optimization
- Initial implementation language: Python
- Contract scope: domain-neutral and provider-neutral

## 1. Purpose

KPO optimizes the external knowledge policy supplied to an Agent. It does not
modify the Agent model's parameters.

Given task cases, a policy snapshot, feedback sources, and evaluation rubrics,
KPO must be able to:

1. execute reproducible Agent rollouts;
2. evaluate those rollouts independently and across multiple dimensions;
3. attribute observed differences to the correct system layer;
4. propose minimal candidate policy changes;
5. test candidates against validation, regression, and ablation suites;
6. promote an approved candidate safely into an allowlisted policy store;
7. retain the evidence needed to explain, reject, deprecate, or roll back a
   policy change.

## 2. Goals

### 2.1 Framework goals

- Remain reusable across people, organizations, disciplines, and task types.
- Keep the model, policy, evaluator, runtime artifacts, and knowledge store as
  separately replaceable components.
- Make every policy change explicit, attributable, reviewable, and reversible.
- Support black-box Agent models and local or remote providers.
- Separate reference fidelity from factual validity and outcome quality.
- Preserve enough execution metadata to reproduce or explain a result.

### 2.2 Safety goals

- Non-promotion commands make zero changes to source knowledge stores.
- Real domain assets never need to enter the KPO Git repository.
- A component that proposes a patch cannot approve that patch.
- A promotion cannot write outside a profile-defined allowlist.
- A failed or interrupted promotion has a documented recovery path.

## 3. Non-goals

KPO v0.1 will not:

- train, fine-tune, or otherwise update model weights;
- claim to recover an individual's private internal reasoning;
- treat similarity to a reference as proof of factual correctness;
- autonomously approve its own policy changes;
- manage remote GitHub publication of domain data;
- provide a hosted multi-tenant service;
- optimize prompts, topology, model choice, and knowledge policy simultaneously;
- include real profiles, corpora, or runtime traces in repository fixtures.

## 4. System boundaries

KPO uses three independent storage boundaries.

### 4.1 Code checkout

Contains generic code, specifications, schemas, and synthetic tests. It is safe
to publish after repository hygiene checks pass.

### 4.2 External profile and source stores

Contain real policy configuration, task sources, reference artifacts, and
knowledge content. KPO receives their locations through explicit configuration.
They are read-only except during an approved promotion.

### 4.3 Runtime data home

Contains runs, model outputs, evaluations, evidence, candidate patches,
snapshots, and journals. It lives outside the code checkout and must be
configurable. No runtime command may silently fall back to writing inside the
repository.

## 5. Core concepts

### 5.1 `PolicyProfile`

An external configuration that binds a KPO run to concrete adapters and rules.
It contains:

- opaque profile ID;
- case-source adapter configuration;
- policy-store adapter configuration;
- reference-provider configuration;
- evaluator configuration;
- promotion allowlist and gate configuration;
- runtime data-home location.

The profile schema is generic. Real profile files are not repository content.

### 5.2 `TaskCase`

A unit of evaluation containing:

- stable case ID;
- task input;
- information cutoff or observation time, when relevant;
- allowed context references;
- tags used for stratification, not for hidden answer leakage;
- references to feedback artifacts that remain hidden from the Actor.

### 5.3 `PolicySnapshot`

An immutable, content-addressed view of the policy used for a rollout. It
records included artifact IDs, versions, retrieval configuration, and digest.

### 5.4 `Rollout`

A complete record of one Actor attempt:

- task-case ID and policy-snapshot digest;
- model/provider identity and decoding configuration;
- retrieved policy artifact IDs;
- output artifact;
- tool events and externally visible reasoning structure, if requested by the
  task contract;
- timing, token, and cost metadata when available;
- completion or failure state.

Private provider reasoning that is not exposed by the provider is neither
required nor inferred.

### 5.5 `ReferenceArtifact`

A feedback source used after Actor completion. Its kind may be:

- expert-authored output;
- observed world outcome;
- deterministic expected result;
- rubric or constraint;
- human evaluation.

The framework must not assume that every reference is correct or that one
reference kind is always authoritative.

### 5.6 `Evaluation`

An immutable evaluator result containing:

- evaluator identity and rubric version;
- dimension-level scores and explanations;
- cited rollout and reference artifact IDs;
- uncertainty and abstention state;
- machine-verifiable checks, when available;
- overall scalar score only as an optional derived value.

Required evaluation dimensions are configurable. KPO must support at least:

- task framing;
- relevant-variable selection;
- evidence use;
- causal or procedural structure;
- scenario and boundary handling;
- conclusion or action alignment;
- calibration and falsifiability;
- factual or outcome validity;
- style, as an optional low-priority dimension.

### 5.7 `Diagnosis`

A classification of why the rollout differed from the desired result. Initial
classes are:

- missing policy knowledge;
- retrieval failure;
- policy-application failure;
- invalid or misapplied rule;
- missing applicability boundary;
- insufficient task evidence;
- reference inconsistency;
- evaluator uncertainty or failure;
- runtime or provider failure.

Only diagnoses that implicate policy content may produce a policy patch.

### 5.8 `CandidatePatch`

A proposed change against one parent policy snapshot. Supported mutation kinds
are:

- add;
- edit;
- split;
- merge;
- reprioritize;
- downvote;
- deprecate;
- add applicability boundary.

Every patch records provenance, diagnosis IDs, affected policy artifacts,
expected benefit, possible regressions, parent digest, and patch digest.

### 5.9 `EvidenceLog`

An append-only record of where a policy artifact or candidate helped, harmed,
or had no measurable effect. Deprecation never deletes the evidence that led to
it.

### 5.10 `PromotionDecision`

A human or independently authorized decision bound to:

- candidate digest;
- regression-report digest;
- exact destination allowlist;
- preview diff digest;
- approver identity;
- timestamp and decision reason.

## 6. Role separation

KPO defines logically isolated roles:

- **Actor** produces a rollout using only the task-visible inputs and policy.
- **Evaluator** scores completed rollouts using hidden references and rubrics.
- **Diagnoser** attributes failures to system layers.
- **Proposer** creates candidate patches.
- **Promotion authority** approves or rejects a tested candidate.

The Actor must not see hidden reference artifacts. The Proposer must not act as
the promotion authority. Evaluator and Actor contexts must be isolated even if
they use the same underlying provider. A profile may require distinct models or
human review for higher-risk use cases.

## 7. Workflow

### 7.1 Run

1. Resolve and validate the external profile.
2. Resolve a task case and freeze its visible inputs.
3. create or load an immutable policy snapshot.
4. Execute the Actor.
5. Persist the rollout in runtime storage.
6. Verify that the source store has not changed.

### 7.2 Evaluate

1. Load a completed rollout.
2. Load hidden references only into Evaluator context.
3. Run deterministic checks before model-based judgment.
4. Produce dimension-level evaluations with citations and uncertainty.
5. Preserve disagreements instead of silently averaging them away.

### 7.3 Diagnose and propose

1. Diagnose the lowest system layer that explains the failure.
2. Refuse policy mutation when the failure belongs to data, retrieval runtime,
   provider, reference, or evaluator layers.
3. When a policy defect is supported, propose the smallest relevant mutation.
4. Persist the candidate outside the source store.

### 7.4 Regress and ablate

1. Evaluate the parent and candidate under matched model and run settings.
2. Run training, validation, and held-out case partitions separately.
3. Re-run relevant historical failures.
4. Perform an ablation that removes the candidate change.
5. Report dimension-level gains, regressions, cost changes, and uncertainty.
6. Never promote solely because a single aggregate score increased.

### 7.5 Promote

1. Default to dry-run.
2. Verify candidate, parent, regression-report, and destination digests.
3. Reject any path outside the profile allowlist.
4. Create a recoverable snapshot of affected destination files.
5. Produce a stable preview diff and digest.
6. Require explicit approval bound to that digest.
7. Apply the exact reviewed mutation through a journaled operation.
8. Verify destination content and record the resulting policy digest.
9. On interruption, report preserved data, remaining mutations, and recovery
   actions without claiming success or rollback prematurely.

## 8. Evaluation and optimization rules

- Preserve score vectors; an aggregate reward is derived, not canonical.
- Keep fidelity, validity, generalization, cost, and regression penalties
  separately visible.
- Use chronological or otherwise distribution-shifted holdouts when task time
  matters.
- Record all retrieved policy artifact IDs to support credit assignment.
- Change one policy component per initial optimization iteration.
- Prefer controlled search or hill climbing in v0.1; model-weight RL is outside
  scope.
- Do not promote a rule without applicability conditions and a failure signal.
- Rules may be deprecated and later restored if new evidence supports them.

## 9. Provider and adapter contracts

Public contracts must not require a specific model vendor.

The initial implementation will define protocols for:

- `ActorProvider`;
- `EvaluatorProvider`;
- `CaseSource`;
- `PolicyStore`;
- `ReferenceProvider`;
- `ArtifactStore`;
- `PromotionTarget`.

Tests use deterministic fake providers. A real provider adapter is implemented
only after core behavior passes against fakes.

## 10. Runtime persistence

KPO v0.1 will use:

- SQLite for run metadata, state transitions, evidence indexes, and journals;
- content-addressed files for larger text artifacts;
- SHA-256 digests for snapshots, candidates, reports, and approval binding.

Runtime writes must be atomic where the operating system supports it. A run has
an explicit state machine so an interrupted operation can be resumed or
reported without repeating completed provider calls.

## 11. Proposed CLI

```text
kpo validate-profile --profile PATH
kpo run --profile PATH --case CASE_ID
kpo evaluate --profile PATH --run RUN_ID
kpo diagnose --profile PATH --run RUN_ID
kpo propose --profile PATH --run RUN_ID
kpo regress --profile PATH --candidate CANDIDATE_ID
kpo promote --profile PATH --candidate CANDIDATE_ID
kpo promote --profile PATH --candidate CANDIDATE_ID --approve DIFF_DIGEST
kpo status --run RUN_ID
```

The first `promote` form is preview-only. The second applies only the exact diff
identified by `DIFF_DIGEST`.

## 12. Repository hygiene

The repository check must fail when tracked content contains:

- runtime or real profile directories;
- non-synthetic datasets or fixtures;
- absolute user paths;
- likely credentials or secrets;
- entries from an optional external local denylist.

The external denylist is never copied into logs or committed. CI performs
generic path, fixture, secret, and absolute-path checks. Local pre-commit checks
may add private denylist enforcement.

## 13. MVP acceptance criteria

KPO v0.1 is complete when all of the following are demonstrated with synthetic
fixtures:

1. A deterministic Actor reads a policy snapshot and produces a rollout.
2. A logically isolated Evaluator uses a hidden reference and emits a score
   vector with citations.
3. A Diagnoser distinguishes a policy defect from retrieval, provider, and
   reference defects.
4. A Proposer creates a minimal, provenance-complete candidate patch.
5. Regression compares parent and candidate on separate partitions.
6. Ablation demonstrates whether the candidate caused the observed change.
7. Non-promotion commands leave a monitored source store byte-for-byte
   unchanged.
8. Promotion preview produces a stable diff without modifying the target.
9. Promotion apply rejects missing approval, stale digests, and paths outside
   the allowlist.
10. An approved promotion creates a snapshot and journal and can be recovered
    after an injected interruption.
11. Repository hygiene rejects a synthetic leak fixture while the real tracked
    tree passes.
12. The full test suite uses no network access and no real domain data.

## 14. Planned TDD sequence after approval

1. Repository hygiene and configuration-boundary tests.
2. Core immutable schemas and digest tests.
3. Runtime state-machine and artifact-store tests.
4. Read-only case and policy adapter tests.
5. Actor/Evaluator isolation tests using fake providers.
6. Diagnosis and candidate-patch provenance tests.
7. Matched regression and ablation tests.
8. Promotion preview, allowlist, approval, journal, and recovery tests.
9. Synthetic end-to-end CLI test.
10. First real provider adapter behind the stable protocols.

## 15. Approval record

The specification was approved on 2026-08-12 with these decisions:

1. Python 3.12 is the v0.1 implementation language.
2. SQLite plus content-addressed files provide runtime persistence.
3. Every applied promotion remains explicitly human-approved in v0.1.
4. Promotion is preview-only unless the exact diff digest is approved.
5. Real profiles and domain data remain external to the repository and enter
   only through explicit configuration.
